# nimbls 安全外部協助：概念與報告摘要

狀態：未來功能設計草稿，**不包含在第一個 milestone**。本地 LLM 仍是初期產品方向；外部協助尚未實作，也未完成安全驗證。技術選型需考慮未來相容性，不代表現在建立 relay 或外送資料。

適用對象：產品、前端 agent、工程、行銷、業務及簡報撰寫者。詳細規則以 [Secure external assistance design](../specs/secure-external-assistance.md) 為準；本文提供易讀摘要。

## 可直接用於報告的說明

> nimbls 規劃以本地模型處理現場任務。當需要外部模型協助時，由本地系統整理最少必要資訊，依資料種類套用安全規則、去敏感化及核准程序，才透過受控的加密通道送出。外部回覆由原本的本地 agent 驗證與接續處理，設備權限和變更核准仍留在本地。每種外送資料必須完成獨立安全 review 與測試，未通過者不啟用。
>
> 這是未來設計方向，不是已交付能力，也不是零洩漏或零留存保證。

## 要解決什麼問題

現場資料可能包含設備識別、網路拓樸、設定、事件、帳號或機密。希望利用外部模型的分析能力，不代表可以把完整日誌、對話或工作目錄送到外部。

因此，產品需要把「模型需要哪些資訊」與「組織允許哪些資訊離開現場」分開處理。外部模型可以提出補件需求，但無權自行取得本地檔案、執行指令或操作設備。

## 建議架構

```text
本地 nimbls 與本地 LLM
        ↓ 提出具體分析問題
最少必要證據 → 逐類安全規則 → 去敏感化 → 必要核准
        ↓ 經認證與加密的主動外連
選用的 nimbls Relay → 外部模型
        ↓ 分析結果或補件要求
本地驗證 → 原本的 agent 接續任務
```

推薦由一個本地 nimbls 搭配選用的輕量 relay，無須為此建立第二個完整 nimbls 或另一個有現場權限的 agent。Relay、Pi、模型引擎及傳輸方式仍是待評估選項，尚未定案。

## 五項核心原則

| 原則 | 產品行為 |
| --- | --- |
| 本地優先 | 預設使用本機或核准的場內模型；不能默默切換到雲端。 |
| 最少必要資訊 | 針對問題整理證據，不預設外送完整原始資料。 |
| 逐類審查 | Syslog、拓樸、設定差異、報告節錄等，各自有規則、review 與測試。 |
| 漸進式披露 | 補件仍需本地權限、政策與必要核准；同時檢查多輪累積揭露。 |
| 本地保留控制權 | 外部提供建議；本地檢查證據，任何設備變更另走核准流程。 |

## 前端應讓使用者看懂什麼

使用者不必理解 sanitizer、policy engine 或 async protocol，但必須知道：

1. 現在是「僅本地」還是允許外部協助。
2. 為什麼需要求助、資料會經過哪個 relay 並送給哪個供應商／模型。
3. 這次準備送出的實際內容、範圍及先前累積分享的範圍。
4. 現在是在等核准、等分析、等補件，還是本地驗證中。
5. 哪些結論有證據支持、哪些仍無法確認，以及結果存在哪裡。

核准必須綁定指定版本的資料與接收對象。資料或對象改變後，舊核准不可沿用。前端只能呈現與提出操作要求，不能成為唯一的權限檢查點。

取消任務不等於收回已送出的資料。外部分析完成也不等於現場問題已解決。畫面必須清楚呈現這些差異。

## 範例：Syslog 分析需要第二意見

以下是假資料示例，不是實測結果。

- 本地 agent 發現 device-A 的 port-3 短時間斷線 12 次，但無法區分線路問題與設備重啟。
- nimbls 準備事件類型、次數、時間區間與別名，移除不必要的原始識別資訊。
- 資料類型通過安全驗證，且使用者核准這份資料後，才送出外部分析。
- 外部模型要求事件前後五分鐘的介面計數，本地系統先檢查是否能讀取、是否允許外送，再準備新的核准內容。
- 若介面計數尚未完成其專屬安全 review／測試，就拒絕外送；模型要求不能取代驗收門檻。
- 外部提出可能原因與建議檢查。本地 agent 核對證據並產生有條件的報告，不將猜測當成已確認根因。

## 每種資料都要有完整 review 與測試

每類資料需要記錄來源及版本、允許／禁止欄位、轉換方式、接收者、用途、核准要求、累積限制、審查負責人與測試證據。

測試需涵蓋正常資料、藏在自由文字或巢狀欄位中的敏感資料、未知格式、惡意指令、多輪資訊拼接、核准失效，以及重試／取消／斷線／錯誤日誌。檢查實際序列化後送出的內容，不只檢查輸入欄位。

**未定義、未 review、未通過測試，一律禁止外送。** Schema、去敏感化邏輯、政策或接收者改變後，需要重新 review 與執行受影響的測試。

## 可以說與不能說

| 可以說的設計目標 | 尚不能宣稱 |
| --- | --- |
| 預設本地處理，外部協助受控且可追溯。 | 已完成安全整合或已可用於正式環境。 |
| 限縮外送資料，逐類審查與驗證。 | 去敏感化等於完全匿名或零洩漏。 |
| 對外通訊需要認證與加密。 | 加密代表接收者看不到或不保留資料。 |
| 回覆回到本地驗證後再接續工作。 | 外部回覆自動證明根因或授權修復。 |

Relay 與供應商收到核准內容後的留存、訓練用途及存取行為仍須分別查證。無外連許可的隔離環境維持本地模式。

## 技術選型時要保留的能力

評估 runtime 是否支持受控工具呼叫、模型路由、持久化非同步狀態、等待與恢復、結構化補件、逐版核准及逐類資料測試。保留清楚的責任分工即可，不為未来需求預先建造整套 relay、外部 agent 平台或通用插件框架。
